# 커스텀 보이스 성경 낭독 스튜디오

예봄성경에서 쓸 **내 목소리 성경 음원**을 로컬 GPU로 만드는 도구.
실시간 아님 — 오프라인 배치 생성 → 절 단위 파일 산출 → (추후) R2 업로드.

- 엔진: Qwen3-TTS 12Hz 1.7B Base (voice clone, ICL)
- 장비: RTX 3060 12GB / torch 2.13 cu126
- **산출 단위: 절(verse)** — 예봄성경 공유 캐시에 그대로 얹기 위함
- **1차 대상 역본: 새번역(rnksv)** — 근거는 아래 "역본 선택" 참조

## 실행

```bash
cd voice
python app.py          # → http://127.0.0.1:7860
```

## 화면 3개

| 탭 | 하는 일 |
|---|---|
| **1. 보이스** | 음원 업로드 → **자동 전사(타임스탬프)** → 구간 선택 → 참조 텍스트(원문/ASR) → 이름 저장 |
| **2. 생성** | 보이스 + 입력(성경 범위 **다중선택** / 직접 입력 / 텍스트 파일) → 예상 시간 → 작업 큐 |
| **3. 검수** | 절별 결과·일치율, 행 클릭 재생, **보류 전체 재생성**, 합본 |

### 보이스 등록에서 놓치기 쉬운 것
- **인트로를 건너뛸 것.** 실제 소재(리딩지저스)는 앞 9.74초가 브랜딩+장 안내였다. 자동 전사의 타임스탬프로 절 경계를 잡는다.
- **참조 텍스트는 `원문 넣기` 권장.** ASR은 "태초"를 "대초"로 잘못 듣는다. 오인식이 참조 텍스트에 들어가면 클로닝 품질이 떨어진다.
- 10~30초 권장.

### 검수는 왜 상시로 붙는가
생성 실패가 **확률적**이다. 같은 절·같은 설정인데 뽑을 때마다 다르다(개역 4절은 4회 중 0회 성공).
그래서 "보이스 한 번 검사"로는 안 되고 **절마다** 검수해야 한다.

```
생성 → 검수 → 불합격이면 자동 재생성(최대 N회)
              └ 상한 초과 시 "보류"로 빼고 다음 절로 진행
최종 → 사람은 "보류 목록"만 확인
```

검수 항목: ① 본문 대조(ASR 역전사) ② 길이 이상(잘림/반복) ③ 무음·절단

#### 검수 임계는 절 길이에 따라 다르다 (`engine.qc_threshold`)
ASR 오차는 보통 1~2글자인데, 짧은 절에서는 그 몇 글자가 일치율을 크게 떨어뜨린다.
`"욥이 대답하였다"`(9자) → ASR `"요비 대답하였다"` = **71%**. 음원은 멀쩡한데 85% 기준이면 불합격이다.
욥기 1,070절에서 이런 오탐이 **보류 30건 중 22건**이었다(전부 요비·수와·엘리호 같은 발음 오인식).

| 절 길이 | 임계 |
|---|---|
| ~15자 | 60% |
| ~30자 | 72% |
| ~60자 | 80% |
| 60자~ | 85% |

#### 구조가 반복되는 절은 한쪽이 통째로 빠진다 (`engine.force_split`)
```
원문: 귀가 말을 알아듣지 못하겠느냐? 혀가 음식 맛을 알지 못하겠느냐?
결과: 귀가 말을 알아듣지 못하겠느냐?                       ← 뒷문장 누락
원문: 어찌하여 너는 우리를 짐승처럼 여기며, 어찌하여 우리를 어리석게 보느냐?
결과: 어찌하여 우리를 어리석게 보느냐?                      ← 앞절 누락
```
30~40자라 길이 기반 분할(재시도 최소 `max_len` 40)이 걸리지 않아 몇 번을 다시 뽑아도 같은 자리가 빠진다.
그래서 **재시도(`tries>=1`)부터는 길이와 무관하게 문장 → (문장이 하나면) 쉼표 단위로 강제 분할**한다.
이 잘림은 `자/초`가 14를 넘어 길이 검수에 먼저 걸리므로 음원으로 새어 나가지는 않는다.

#### 임계를 고친 뒤엔 이미 보류된 절을 되살린다
```bash
python recheck_held.py --book 욥기 --dry   # 판정만 확인
python recheck_held.py --book 욥기         # 통과분 합격 처리 + 나머지 재생성 큐(tries=1)
```
비율만 보고 통과시키지 않는다 — ASR 을 **다시 돌려** 현재 기준으로 재판정한다.
재생성으로 넘기는 절은 `tries=1` 로 올려 첫 시도부터 강제 분할이 걸리게 한다.

## 구성

| 파일 | 역할 |
|---|---|
| `app.py` | Gradio UI (얇은 층) |
| `engine.py` | 모델 싱글톤·보이스·본문조회·합성·QC (UI/CLI 공용) |
| `jobs.py` | 작업 큐·상태파일·워커·재시도·재개 |
| `prosody.py` | 끊어읽기 보정(구두점 주입·대시 정리·가변 무음) |
| `gen_verses.py` / `qc_asr.py` | CLI (UI 없이 밤새 돌릴 때) |
| `recheck_held.py` | 보류 절 재검수(임계 변경 후 오탐 회수) |
| `smoke_job.py` | 파이프라인 통합 점검 |
| `prep_ref.py` / `transcribe_full.py` | 참조 클립 준비(초기 1회) |

상태는 `jobs/*.json`에 남아 **앱을 껐다 켜도 이어진다**. 이미 만든 절은 건너뛴다.

> **워커는 한 번에 하나만.** `app.py`(UI)와 `run_book.py`/`run_plan.py` 는 각자 워커를 띄운다.
> 같은 PC 에서 둘을 동시에 돌리면 같은 작업을 양쪽이 집어 같은 절을 두 번 만들고,
> 각자 메모리의 job 을 저장하며 서로의 진행을 덮어쓴다.
> 장시간 생성은 `run_plan.py` 로만 돌리고, 검수는 생성이 멈춘 뒤 `app.py` 로 연다.
> (`engine.py`/`jobs.py` 를 고쳤다면 **워커를 재시작해야** 반영된다 — 실행 중인 프로세스는 옛 코드를 물고 있다.)

## 파일럿에서 확인된 것

### 배치 크기별 속도 (개역 요일 1장)
| 배치 | RTF | 새번역 전량(87.3h) 환산 |
|---|---|---|
| 기존 | 2.61 | 9.5일 |
| 2 | 1.56 | 5.7일 |
| **4** | **0.96** | **3.5일** |
| 8 | 0.89 | 3.2일 |

→ **배치 4~8 권장** (3060 12GB에서 8까지 OOM 없음).

### 역본 선택 — 새번역으로 가는 이유
같은 조건(4회 반복)으로 어미 보존율을 측정:

| | 개역 | 새번역 |
|---|---|---|
| 어미 보존 | **25%** (3/12) | **67%** (8/12, 실패분은 ASR 오인식 '사귐→사김') |
| 구두점 | 0개 | 36개(1장) |
| 통합 테스트 최저 일치율 | 78% | **95%** |

개역은 고어 종결어미가 **현대어로 정규화**된다(`하려 함이라` → `하려 합니다`). 성경 본문 훼손이라 허용 불가.
새번역은 이미 현대어라 그 위험이 없고, 구두점이 본문에 있어 끊어읽기도 자연스럽다.
게다가 예봄성경엔 **개역·쉬운성경 사람 녹음이 이미 있고 새번역만 없다** — 필요한 곳과 안전한 곳이 일치한다.

### 본문 처리 (prosody.py)
- **개역**(구두점 0개): 연결어미 뒤 쉼표, 절 끝 종결/연결에 맞춰 마침표·쉼표 주입
- **새번역**(구두점 있음): **손대지 않음** — 덧붙이면 `합니다.,` 같은 이중 부호가 된다
- **양끝 대시 제거**: 새번역 삽입구의 닫는 `-` 가 절 끝에 남는 경우가 있다(요일 1:1, 1:2)
- 절 사이 무음: 종결 0.55초 / 연결 0.15초

> 이 변형은 **생성 입력에만** 적용한다. 예봄성경 공유 캐시 키는 `sha1(원문)` 이라 원문을 바꾸면 안 된다.

## 예봄성경 연결 (예정)

`/api/tts` 는 합성 전 R2 공유 캐시를 먼저 본다:

```
tts/v1/ko/{voiceKey}/{sha1(정제본문)}.mp3
```

생성물을 이 키로 올리면 **서버 코드 수정 없이** 서빙된다(`engine.cache_key()` 가 같은 규칙).
정제 규칙(`NOTE_RE`)은 서버와 문자 단위로 동일해야 한다 — 어긋나면 조용히 캐시 미스가 난다.

## 다른 PC 에 설치하기

**예봄성경 로그인 → 설정 → 관리자 → 음원 생성 PC 설치 → [설치 파일 받기]**
받은 `예봄성경-음원생성-설치.bat` 를 그 PC 에서 더블클릭하면 끝이다.

git, GitHub 계정, Node, `.env.local` 복사, 참조음 복사 — **전부 필요 없다.**
설치 파일 안에 기기 토큰이 들어 있어서, 나머지는 서버에서 받아온다.

### 사람이 해야 하는 일은 두 가지뿐

1. **NVIDIA 그래픽카드가 있는지 확인** (RTX 3060 12GB 이상 권장)
   작업 관리자(Ctrl+Shift+Esc) → 성능 → GPU 에 "NVIDIA" 가 보이면 된다.
   없으면 설치가 첫 단계에서 멈춘다 — CPU 로는 한 권에 몇 주가 걸려 의미가 없다.
2. **Windows 경고에서 "추가 정보 → 실행"** — 인터넷에서 받은 배치파일이라 한 번 나온다.

그 외에 첫 설치 때 약 **6GB** 를 내려받는다(10~40분). 디스크는 15GB 이상 비워 둔다.

### 설치 프로그램이 대신 하는 일

| 단계 | 내용 |
|---|---|
| 1 | 그래픽카드·VRAM 확인 (없으면 여기서 중단) |
| 2 | 파이썬 없으면 winget 으로 설치 |
| 3 | torch(cu126)·qwen-tts·faster-whisper·gradio·ffmpeg 설치 |
| 4 | 스튜디오 소스를 서버에서 내려받기 |
| 5 | 보이스(참조음)를 서버에서 내려받기 |
| 6 | 로컬 화면 실행 + `yebomtts://` 등록 |

다시 실행하면 이미 된 단계는 건너뛴다 — **설치 스크립트가 곧 갱신 스크립트**다.
소스는 매번 서버와 대조하므로 캐시 키 규칙이 서버와 어긋날 일이 없다.

### 주석이 섞인 본문은 만들지 않는다

편집자 주석은 괄호 안에 들어가고 낭독에서 제외된다(`NOTE_RE`). 그런데 **여는 괄호가
빠진 채** 들어간 절이 있다. 그러면 주석이 본문으로 남아 **소리 내어 읽힌다.**
검수는 통과한다 — 잘못된 원문과 음원이 일치하기 때문이다.

대조본 없이 판별할 객관적 기준은 **괄호 짝**이다. 여는 괄호가 사라지면 닫는 `)` 만 남는다.

```
욥기 1:5  …신중하였다.', 히브리 본문에서는 … '서기관의 대치(티쿤 쏘프림)'라고 함)
                                                                            ↑ 짝 없음
열왕기상 22:20  '이렇게 하자' 또는 '저렇게 하자' 하며   ← 괄호가 맞음 = 본문
```

새번역 31,075절 중 **16절**이 걸렸고, `또는 '…'` 같은 본문 표현은 걸리지 않았다.
생성 전에 이런 절을 보류로 빼서 중앙 검수로 올린다 — 사람이 **본문을 고쳐야** 하는 일이다.

> 본문을 고치면 키(본문 sha1)가 바뀌므로 잘못 만든 음원은 자동으로 서빙에서 빠지고,
> 건너뛰기 대조가 "없는 절" 로 잡아 다시 만든다. 손으로 지울 것이 없다.

### 이미 만들어진 절은 건너뛴다

책 하나를 시작할 때 서버에 **"이미 있는 절 목록"** 을 한 번 물어보고, 있는 것은 생성하지 않는다.
PC 를 몇 대로 늘리든 같은 절을 두 번 만들지 않으므로, 어느 PC 에 어느 책을 맡길지
정밀하게 나눌 필요가 없다.

| 시점 | 왜 |
|---|---|
| 절마다 | 왕복이 수만 번 — 느리다 |
| 작업 걸 때 한 번 | 며칠 뒤 만들 책까지 그 시점으로 판정 — 그 사이 다른 PC 가 만든 걸 놓친다 |
| **책 시작할 때 한 번** | 왕복 1회로 그 책 전체를 거르고, 항상 최신 상태를 본다 |

공유 캐시 키가 본문 sha1 이라 **존재하는 키 목록만 받아 로컬에서 대조**하면 된다
(욥기 완료 시점 기준 1,078개 = 44KB). 서버가 안 되면 아무것도 건너뛰지 않고
그냥 전부 생성한다 — **어떤 경우에도 멈추지 않는다.**

> 덤으로 **본문이 바뀐 절을 찾아낸다.** 욥기 1:5 는 생성 당시 본문(274자)에
> 편집자 주석이 섞여 있다가 나중에 정리되어(186자) 키가 달라졌다. 그때 만든 음원은
> 주석을 소리 내어 읽는데, 검수는 통과했다 — 잘못된 원문과 음원이 일치했으니까.
> 내용 주소 방식이라 본문이 바뀌자 그 음원은 자동으로 서빙에서 빠졌고,
> 건너뛰기 대조가 그 사실을 드러냈다.

### 보류 절은 한 곳에서 판단한다

검수(탐지)는 자동이지만 **판단은 자동화되지 않는다.**

| 절 | 글자 일치 | 자모(소리) 일치 | 실제 |
|---|---|---|---|
| 욥이 대답하였다 → "요비 대답하였다" | 71% | 93% | 오탐 |
| 수아 사람 빌닷이 → "수와 사람 빌다시" | 75% | 92% | 오탐 |
| **욥기 39:8** ("푸른 풀은"→"풀은 풀른") | 67% | **88%** | **진짜 오류** |

연음 오인식을 걷어내려고 자모(소리) 단위 비교를 시험했으나, **어순이 뒤바뀐
진짜 오류도 88%로 통과**해버린다. 오탐을 없애려다 진짜 오류를 놓치므로 쓰지 않는다.
마지막 판단은 사람이 원문·ASR 을 나란히 보고, 애매하면 들어 보고 정해야 한다.

PC 가 여러 대면 그 판단거리가 각 PC 의 `jobs/*.json` 안에 흩어져 아무도 못 본다.
그래서 보류 절을 음원과 함께 서버로 보고하고, **설정 → 관리자 → 음원 보류 절 검수**
한 화면에서 처리한다.

| 판단 | 하는 일 |
|---|---|
| 이대로 사용 | 서버가 보관 중인 음원을 바로 공유 캐시에 넣는다. **생성 PC 가 꺼져 있어도 즉시 반영** |
| 재생성 요청 | 그 절을 만든 PC 가 작업 중에 가져가 다시 만든다(강제 분할 적용) |
| 비워 둠 | 그대로 둔다 — 그 절만 Chirp(여) 폴백으로 읽힌다 |

> **보류 절은 업로드되지 않는다.** 그래서 판단이 늦어도 교인에게 잘못된 본문이
> 나가지 않는다. 최악이 "그 절만 다른 목소리"이고, 성경 본문이 훼손되는 방향으로는
> 실패하지 않는다.
>
> 재생성 요청은 **한 번만** 처리한다. 다시 실패해도 요청은 서버에 남아 있는데
> 그걸 매번 집으면 같은 절을 무한히 반복 생성하게 된다.

### 설치되는 위치 / 두 번째부터 켜는 법

| | |
|---|---|
| 설치 폴더 | `%LOCALAPPDATA%\YebomVoice` |
| 두 번째부터 | **바탕화면의 `예봄성경 음원생성.bat`** |

설치 폴더가 `%LOCALAPPDATA%` 안이라 사람이 찾아가기 어렵다 — 설치 마지막에
바탕화면에 실행 파일을 두고, 그 이름을 화면에 크게 알려준다.
바탕화면은 OneDrive 로 옮겨져 있는 경우가 흔해서 레지스트리에서 실제 경로를 읽는다.

실행 파일(`실행.bat` · 바탕화면 `예봄성경 음원생성.bat`) 규칙 — `bootstrap.py` 의 `launcher_bytes()`:

| 규칙 | 이유 |
|---|---|
| 줄 끝 **CRLF**, 바이트 그대로 복사 | 예전엔 바탕화면에 글자로 옮기며 LF 가 되어, cmd 가 한글 창 제목 줄을 잘못 끊어 조각을 명령으로 실행했다 — `'?깃꼍'은(는) 내부 또는 외부 명령…`, 주소 조각을 네트워크 경로로 열려다 `액세스가 거부되었습니다` + 'Windows 보안 — 파일을 복사할 수 없음' 창 |
| **영문·숫자만** | 경로는 `%LOCALAPPDATA%\YebomVoice` 처럼 적어 사용자 이름이 한글이어도 한글이 남지 않는다. 창 제목 같은 한글은 파이썬이 단다. 그래도 한글이 남으면(드묾) CP949 + `chcp 949` |
| 짧게(주석 없음) | 옛 실행 파일이 도는 중에 바꿔 쓰면 cmd 는 파이썬이 끝난 뒤 옛 자리부터 새 파일을 읽는다 — 새 파일이 더 짧으면 그냥 끝난다 |

이미 설치된 PC 는 켤 때마다 고친다(`repair_launchers()` — `bootstrap.py --run` 과 `app.py` 시작 시).
`bootstrap.py` 도 스튜디오 소스와 함께 켤 때마다 새로 받으므로(`/api/voice-studio/code`), 옛 설치도
**한 번 켜면** 실행 파일이 고쳐지고 그다음부터 오류 메시지가 사라진다.

### PC 가 꺼졌다 켜지면

**바탕화면의 `예봄성경 음원생성.bat` 을 더블클릭하면 끝이다.** 하던 작업을 자동으로 이어간다.
이미 만든 절은 건너뛰므로 처음부터 다시 하지 않는다.

작업 상태는 `jobs/*.json` 에 매 배치마다 저장되므로, 갑자기 전원이 나가도
마지막 배치(최대 4절)만 다시 만든다.

> 예전에는 앱만 뜨고 워커가 시작되지 않아, 사람이 '이어하기' 를 누르기 전까지
> 아무 일도 일어나지 않았다. 며칠짜리 작업에서는 치명적이라 자동으로 바꿨다.

### 어디까지 왔는지 보기

여러 권을 한 작업으로 걸면 총계("64/20530")만으로는 아무것도 알 수 없다.
**책별 진행** 표에 한 권씩 나온다.

```
책        상태     진행               보류  업로드  마지막 절
출애굽기   완료     1213/1213 (100%)    3   1210   출애굽기 40:38
레위기     진행중    320/859 (37%)      2    315   레위기 11:12
민수기     대기      0/1288 (0%)        0      0
신명기     대기      0/959 (0%)         0      0
```

작업 표에는 한 줄 요약이 함께 나온다 — `레위기 320/859 · 1/4권`.
절 참조("출애굽기 3:14")에서 책 이름을 뽑아 원래 순서대로 묶는다.

### 안 될 때는 [서버 연결 확인]

생성 탭의 `서버 연결 확인` 버튼이 어느 단계에서 끊겼는지 알려준다.
시작할 때 성경 본문을 못 가져오면 자동으로 펼쳐진다.

```
1. 접속 정보   OK   https://bible.yebom.org
2. 서버 응답   OK   토큰 만료 2027-03-08
3. 성경 본문   OK   새번역 66권
4. 보이스      OK   영희
5. ffmpeg      OK
```

책 목록이 비어 있으면 대개 3번이 실패한 것이다. 예전엔 빈 목록만 남아
왜 안 되는지 알 수 없었다.

### 책 고르기

| 방법 | 쓸 때 |
|---|---|
| 신약 전체 / 구약 전체 / 전체 | 통짜로 맡길 때 |
| **범위 시작 ~ 범위 끝 + [범위 선택]** | "출애굽기부터 구약 전체" 처럼 중간부터 맡길 때 |
| 책 체크박스 | 몇 권만 집을 때 |

범위는 성경 순서를 따르고, 시작·끝을 거꾸로 골라도 알아서 뒤집는다.

> 빠른 선택 버튼은 **책 목록(choices)도 함께 채운다.** 목록이 아직 안 채워진 상태에서
> 누르면 "목록에 없는 값을 선택"하게 되어 컴포넌트가 오류를 냈다.

### 생성하면 자동으로 예봄성경에 올라간다

생성 탭의 `완성된 절을 예봄성경에 자동 업로드` 가 켜져 있으면, **검수를 통과한 절이
그때그때** 공유 캐시로 간다. 책이 끝나기를 기다리지 않으므로, 며칠짜리 작업이
중간에 끊겨도 그때까지 만든 음원은 이미 교인에게 서빙되고 있다.

CLI 도 같다 — 보이스 `meta.json` 의 `voiceKey`(영희=f4)를 보고 알아서 올린다:

```bash
python run_plan.py --voice 영희 --start 욥기      # 자동 업로드 켜짐
python run_plan.py --voice 영희 --start 욥기 --no-upload   # 생성만
```

> 성경 본문일 때만 올린다. 직접 입력·텍스트 파일은 공유 캐시 키(본문 sha1)에
> 얹을 근거가 없으므로 생성만 한다.

### 로컬에 비밀키를 두지 않는다

업로드는 **로컬 → 예봄성경 서버 → R2** 로 간다. 예전처럼 각 PC 에 R2 비밀키를
복사하지 않는다 — PC 가 늘수록 키가 퍼지고 한 대만 분실돼도 저장소 전체가
노출되기 때문이다. PC 를 회수할 땐 그 토큰 하나만 폐기하면 된다.

키도 **서버가 본문으로 직접 계산한다.** 로컬이 계산한 키는 받지 않는다 —
로컬 코드가 어긋나 엉뚱한 키로 올라가면 에러 없이 조용히 캐시 미스가 나기 때문이다.

성경 본문 조회에 쓰는 Supabase 키는 이미 브라우저 번들에 들어 있는 **공개 anon 키**라
서버가 내려줘도 된다. 그래서 `.env.local` 복사가 사라졌다.

### 보이스를 서버에 등록하려면 (관리자, 기존 PC 에서 1회)

```bash
python push_voice.py --voice 영희 --voice-key f4 --gender female --session <쿠키값>
```

`--session` 은 브라우저에서 예봄성경에 관리자로 로그인한 뒤
개발자도구(F12) → 애플리케이션 → 쿠키 → `saint_record_session` 값이다.
등록 후에는 새 PC 가 이 참조음을 그대로 받아간다.

## 여러 PC 로 분담 생성

새번역 전권은 1대로 약 **5.4일**(129시간)이다. PC 를 늘리면 그만큼 줄어든다.

### 반드시 지킬 것 — 보이스 지문

**참조 클립이 1초라도 다르면 음색이 미묘하게 달라져 책마다 목소리가 바뀐다.**
듣기 전에는 알아채기 어렵고, 알아챘을 땐 이미 수천 절을 만든 뒤다.
그래서 각 PC 에서 지문이 **같은지 먼저 확인**한다.

```bash
python -c "import engine; print(engine.voice_fingerprint('영희'))"
```

`voice/voices/{보이스}/` 폴더(ref.wav + meta.json)를 **파일 그대로 복사**하면 지문이 같다.
절대 2번째 PC 에서 참조 클립을 다시 잘라 등록하지 말 것.

### 2번째 PC 준비

위 "다른 PC 에 설치하기" 대로 설치 파일 하나만 실행하면 된다.
참조음도 서버에서 같은 파일을 받으므로 **지문이 자동으로 일치한다** —
2번째 PC 에서 참조 클립을 다시 자르는 일은 절대 하지 말 것.

### 작업 분담

```bash
# PC1 — 구약 (진도표 순서)
python run_plan.py --voice 영희 --start 욥기 --testament old

# PC2 — 신약 (진도표 순서)
python run_plan.py --voice 영희 --start 욥기 --testament new

# 특정 책만 (분담 미세조정)
python run_plan.py --voice 영희 --only 시편,예레미야,이사야
```

### 왜 잠금·조율이 필요 없는가

R2 키가 `tts/v1/ko/{성우}/{sha1(정제본문)}.mp3` 로 **내용 주소**다.
- 서로 다른 책 → 키가 절대 겹치지 않는다
- 실수로 같은 절을 두 번 만들어도 → 같은 키에 같은 내용이 덮여 쓰일 뿐

각 PC 가 **각자 R2 에 직접 업로드**하면 되고, 산출물을 한곳에 모을 필요가 없다
(wav 를 옮기면 수 GB, mp3 로 R2 직행이면 훨씬 가볍다).

### 분량과 소요 (실측 0.21초/자 기준)

| 구분 | 권수 | 절 | 글자 | 예상 |
|---|---|---|---|---|
| 구약 | 39 | 23,133 | 1,679,495 | **98시간** |
| 신약 | 27 | 7,942 | 532,144 | **31시간** |
| 전체 | 66 | 31,075 | 2,211,639 | 129시간 |

구약이 76% 라 단순 구약/신약 분담은 4.1일 : 1.3일로 기운다.
**PC2 가 신약을 끝내면(약 1.3일) 구약 큰 책을 넘겨받는 방식**을 권한다:

```bash
# PC2 2단계 — 뒤쪽 큰 책을 가져간다
python run_plan.py --voice 영희 --only 시편,예레미야,이사야,에스겔,민수기
```

이렇게 하면 양쪽 약 2.7일로 맞아 전체 기간이 절반이 된다.
진도표 앞쪽(욥기·창세기·출애굽기…)은 PC1 이 순서대로 만들므로
교인이 읽는 순서에는 구멍이 생기지 않는다.

### 각 PC 에서 업로드

생성 중에 자동으로 올라가므로 따로 할 일은 없다. 전수 재검증만 필요하면:

```bash
python qc_sweep.py --voice 영희 --book 마태복음
```

`upload_r2.mjs` (Node + R2 비밀키 방식)는 서버 경유 업로드로 대체되었다.

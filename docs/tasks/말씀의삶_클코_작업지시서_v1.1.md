## 0. 한 줄 요약

예봄성경에 하단 6번째 탭 **말씀의삶**을 추가한다. 예봄교회 '성경읽기진도표' 91회차 순서로 함께 읽는 성경북클럽 기능이다. **성경 본문·역본 비교·TTS·글꼴은 한 줄도 바꾸지 않는다.** 91회차 순서는 본문 위에 얹는 얇은 '플랜' 층이며, 기존 `reading_progress`(장 단위 자동 기록)에서 회차 완료를 **파생 계산**한다.

작업 순서는 **단계 0(진도 페이지네이션) → 1(플랜 데이터) → 2(진도표·탭) → 2.5(장 이동 통합) → 3(플랜 모드 읽기) → 4(그룹)**이다. 0·1·2.5는 각각 단독으로 확인받는다.

## 2. 절대 금지

- 성경 본문 렌더링·역본 셀렉터·대역·TTS·글꼴·스크랩·카드빌더 로직 수정 금지. 플랜 모드는 **외부에서 위치를 주입**하는 방식으로만 SearchPanel에 개입한다.
- `reading_progress` 스키마·UNIQUE·3초 트리거 변경 금지.
- 91회차 데이터를 "정경 순으로 고치기", "중복 제거", "누락 보완" 금지. **종이 진도표 그대로 옮긴다.** 이상한 곳은 §3.4 확인 사항으로 보고만 한다.
- 자동 commit/push 금지(AGENTS.md 1).
- 보류 사항은 `plan.md`에만 누적(AGENTS.md 2).
- **TTS 파이프라인 수정 금지** — 캐시 키·프리페치·엔진 라우팅·폴백은 손대지 않는다. 허용 범위는 '다음 장 좌표'와 '위치 참조 방식' 둘뿐이다(§5.2).
- **`posRef`는 effect에서만 쓴다.** 로더가 반환 직전에 ref를 전진시키는 구현 금지(§5.2 사유).

## 2A. 단계 0 — `reading_progress` 페이지네이션 (선행 · 단독 확인)

말씀의삶과 무관하게 **이미 존재하는 버그**다. 단계 1보다 먼저 처리하고 단독으로 확인받는다.

### 2A.1 문제

`app/api/reading-progress/route.ts` GET에 `.range()`가 없다. PostgREST 기본 상한 1,000행에서 잘린다. 91회차 완주는 1,188장이므로 **구조적으로 100%에 도달할 수 없다.** 시안 D의 "완주 1명"이 거짓이 된다.

더 나쁜 것은 POST가 재열람마다 `read_at`을 갱신한다는 점이다(같은 파일 64행). 정렬이 `read_at desc`라 **잘려나가는 188장이 매번 달라진다.** 어제 욥기를 다시 열면 오늘은 다른 장이 미완료로 돌아간다. 증상이 흔들려 원인 추적이 어렵다.

그룹 순위는 더 이르다. 멤버 합계가 1,000행을 넘는 순간(8명 × 125장) 경고 없이 잘린 부분집합으로 순위가 계산된다.

### 2A.2 지시

- `lib/supabasePaginate.ts`(또는 동등 위치)에 `.range()` 루프 공용 헬퍼 1개.
- `reading-progress` GET에 적용. 이후 멤버 다건 조회(§6.2 standings)도 같은 헬퍼를 쓴다.
- 다른 무제한 `select`가 더 있는지 훑고 **목록만 보고**한다. 이번에 함께 고치지 않는다(AGENTS.md 3).

### 2A.3 완료 조건

테스트 계정에 1,188행을 넣고 수정 전후 반환 행수 비교(1,000 → 1,188). 결과 보고 후 단계 1로 넘어간다.

## 3. 단계 1 — 플랜 데이터 + 판정 유틸

### 3.1 파일

### 3.2 타입·유틸 (시그니처 고정)

```ts
export interface PlanRange {
  book: string;      // lib/books.ts code
  fromCh: number;
  toCh: number;
  fromVs?: number;   // 절 경계 표기용. 판정에는 쓰지 않는다
  toVs?: number;
}
export interface PlanUnit { seq: number; label: string; ranges: PlanRange[] }
export interface ReadingPlan { id: "yebom91"; name: string; units: PlanUnit[] }

/** 회차의 장 목록. 같은 회차 안 중복 장(예: 10회차 민수기 9)은 1회만, 등장 순서 유지 */
export function unitChapters(unit: PlanUnit): { book: string; chapter: number }[];

/** 플랜 전체를 읽기 순서대로 펼친 배열. 경계 장은 회차마다 다시 등장한다(양쪽 소속) */
export interface PlanChapter { seq: number; book: string; chapter: number; idx: number }
export function flattenPlan(plan: ReadingPlan): PlanChapter[];

/** 현재 위치의 플랜 인덱스. (seq, book, chapter) 로 찾는다 — 경계 장은 seq 로 구분 */
export function findPlanIndex(flat: PlanChapter[], seq: number, book: string, chapter: number): number;

export type UnitStatus = "done" | "partial" | "todo";
export interface UnitProgress { seq: number; status: UnitStatus; readCount: number; total: number; manual: boolean }
export interface PlanProgress {
  units: UnitProgress[];
  doneCount: number;           // 완료 회차 수
  currentSeq: number;          // 가장 낮은 미완료 seq. 전부 완료면 91
  nextChapter:  { seq: number; book: string; chapter: number } | null; // currentSeq 안에서 안 읽은 첫 장
  entryChapter: { seq: number; book: string; chapter: number } | null; // 진입용 — 아래 규칙
}
/** 경계 장: 두 회차 이상에 등장하는 장 10개 (§3.4). 플랜에서 계산해 상수화한다 */
export function boundaryChapters(plan: ReadingPlan): Set<string>;  // key: `${book}:${chapter}`
export function computeUnitProgress(
  plan: ReadingPlan,
  readByBook: Record<string, Set<number>>,   // lib/reading-progress computeProgress().readByBook 그대로
  manualSeqs: Set<number>,
): PlanProgress;
```

판정 규칙:
- `total` = `unitChapters(unit).length`, `readCount` = 그중 `readByBook[book]`에 있는 장 수
- `done` = `manual` 이거나 `readCount === total`
- `partial` = `!done && readCount > 0`
- `currentSeq` = status !== "done" 인 최소 seq. 없으면 91
- `nextChapter` = currentSeq 회차의 `unitChapters` 중 **첫 미읽 장**. 수동 완료 회차는 건너뜀
- `entryChapter` = currentSeq 회차에서 **읽은 장이 하나도 없거나, 읽은 장이 전부 경계 장뿐인 경우** → `unitChapters[0]`. 그 외 → `nextChapter`

`entryChapter`가 따로 필요한 이유는 이렇다. 39회차에서 왕하 15장을 읽으면 3초 트리거가 15장 전체를 읽음 처리한다. 40회차(왕하 15:23-17)의 `nextChapter`는 15장을 건너뛰고 16장을 가리키므로 **15:23-끝을 영영 읽지 않고 40회차가 완료된다.** 경계 장이 회차 맨 앞에 오는 6개 회차(40·50·54·69·83·84)가 전부 해당한다.

반대로 "경계 장은 읽음이어도 건너뛰지 않는다"를 `nextChapter` 규칙에 넣으면 안 된다. 순수 함수라 '이미 제시했음'을 기억할 수 없어 **같은 경계 장이 영원히 반환되는 고정점**이 된다. 83회차에서 고린도후서를 다 읽는 내내 "다음 읽을 장: 사도행전 19장"이 굳는다. 그래서 진입과 표시를 필드로 분리한다.

| 용도 | 사용 필드 |
|---|---|
| 진도표 행 탭 · 플랜 모드 진입 | `entryChapter` |
| 진도표 부제 "다음 읽을 장" · 헤더 진행 표시 | `nextChapter` |

남는 구멍 하나는 인정하고 로직으로 막지 않는다. 40회차의 나머지 장을 먼저 다 읽으면 15장이 이미 읽음이라 회차가 자동 완료되어 `entryChapter`가 호출되지 않는다. 장 단위 판정을 택한 대가다. 대신 **플랜 헤더 칩에 `15:23부터` / `15:22까지`를 반드시 노출**해 사람이 알아보게 한다.

### 4.6 단계 2.5 — 장 이동 통합 (동작 변경 없음 · 단독 확인)

플랜 개입 전에 **동작을 바꾸지 않는 순수 정리**를 먼저 끝낸다. 이 단계와 단계 3을 한 커밋에 섞지 않는다.

**왜 필요한가.** `setChapter(chapters[idx±1])` 호출 지점이 흩어져 있고, 활성 판정도 별도로 박혀 있다. `goChapter` 안만 바꾸면 나머지 경로는 정경 순서로 가고, 활성 판정에 막힌 경로는 **호출조차 되지 않는다.**

| 위치 | 조작 | 활성 판정 |
|---|---|---|
| 1583 `goChapter` | 스와이프 | `canPrevChapter` / `canNextChapter` |
| 1718 / 1732 | PC 좌우 여백 | **1715 / 1729 렌더 조건** — 버튼 자체가 없음 |
| 1769 / 1774 | 풀스크린 오버스크롤 | **1768 / 1773 삼항** — 콜백이 undefined |
| 2348 / 2367 | 상단 ◀▶ 버튼 | **2348 / 2367 disabled** — 회색 |
| 584 / 589 / 601 | 키보드 ← → Space | **578-579 지역 재계산** |

`chapters`는 같은 책 안의 장 목록이라 `canNextChapter`는 책 마지막 장에서 false다. 플랜 이동이 가장 필요한 지점이 바로 거기다. 비활성 지점은 ▶ 67곳, ◀ 65곳이며, 교인이 첫 주에 만나는 3회차 욥기 42장 → 4회차 창세기 1장이 여기 걸린다.

**작업**
1. 위 5개 경로(TTS 제외)를 `goChapter(delta)` 하나로 모은다.
2. `canPrev` / `canNext`를 **단일 파생값**으로 만들고 렌더 조건·삼항·disabled·키보드가 전부 그것을 참조하게 한다. 578-579 지역 계산 제거.
3. `onPositionChange?(book, chapter)` **순수 보고 콜백**을 추가한다. 위치가 바뀔 때마다 호출만 한다. 소비자는 단계 3에서 붙인다.

**완료 조건**: 플랜과 무관하게 기존 동작이 동일함을 확인(스와이프·여백·풀스크린·◀▶·키보드 5경로 + 책 경계에서 여전히 비활성). 스크린샷 대신 경로별 확인 체크리스트로 보고.


- 진도표 행 탭 → 그 행의 `entryChapter`로 `setPlanMode({seq})` + `setView("search")` + `navRequest`(`target: "chapter"`, `book`, `chapter` 추가 — 기존 target 4종 불변)
- `planIdx === -1`이면 플랜을 벗어난 것이다. 헤더를 **"플랜에서 벗어남 · N회차로 돌아가기"**로 바꾼다. 탭하면 `entryChapter`로 복귀
- 목차·검색·책갈피 탭 → `setPlanMode(null)`. 본문 탭은 유지

**seq 확정 규칙**

> 현재 seq는 **진입 시점에 확정하고 플랜 이동으로만 갱신한다.** 행 탭 진입은 그 행의 seq, 선형 이동은 도착 항목의 seq.

역대상 9장처럼 인접 회차에 걸친 장은 어떻게 들어왔는지가 헤더 회차를 결정한다. 두 경로 모두 헤더가 54회차로 일치하므로 엇갈리지 않는다.

**인접 중복 장 — 방향 무관 규칙**

53회차 끝(역대상 9)과 54회차 첫 장(역대상 9)이 붙어 있어, 그대로 두면 "다음"을 눌러도 본문이 그대로다.

> 플랜 이동 시 **도착 항목이 출발 항목과 같은 장이면 한 칸 더 진행한다. 방향과 무관하다.** seq는 최종 도착 항목이 결정한다.

| 방향 | 결과 |
|---|---|
| 정방향 | 대상 9(53) → [대상 9(54) 건너뜀] → 대상 10(54) |
| 역방향 | 대상 10(54) → 대상 9(54) → [대상 9(53) 건너뜀] → 대상 8(53) |

한쪽만 적용하면 역방향에서 역대상 9장이 두 번 나온다.

### 5.2 SearchPanel 개입 지점

props 추가:

```ts
planNav?: {
  header: React.ReactNode;                 // 플랜 헤더 카드 (page.tsx 조립)
  prev: { book: string; chapter: number; label: string } | null;
  next: { book: string; chapter: number; label: string } | null;
  onGo: (t: { book: string; chapter: number }) => void;
};
unitChapters?: { book: string; chapter: number }[];   // 현재 회차 장 목록
onUnitComplete?: (seq: number) => void;
onPositionChange?: (book: string, chapter: number) => void;   // 단계 2.5 에서 이미 추가
fullscreenCloseNonce?: number;
```

**(1) 이동 — `goChapter` + 단일 `canPrev`/`canNext` 두 곳만 오버라이드한다.** `planNav`가 있으면 `prev`/`next`로 `onGo`, 활성 판정은 `planNav.prev !== null` / `planNav.next !== null`. 단계 2.5에서 5경로가 이미 여기로 모였으므로 이 두 곳이면 전부 따라온다.

**(2) 회차 완료 — 델타가 아니라 결과를 올린다.** page.tsx에는 기준 집합이 없어 `onChapterRead(book, chapter)` 튜플 하나로는 "나머지 12장이 이미 읽혔는지"를 알 수 없다. SearchPanel이 자기 `readChapters`로 전이를 감지해 `onUnitComplete(seq)` **하나만** 올린다. 3초 트리거는 재열람마다 발화하므로(629행이 기존 읽음 여부를 검사하지 않음) **이미 완료된 회차에서는 발화하지 않도록** 조건을 건다.

**(3) TTS 자동 다음 장 — 플랜 순서를 따르게 한다.** 플랜 모드에서 기능을 끄지 않는다. 고령 교인이 가장 많이 쓰는 기능이 플랜 안에서만 죽는 것은 기능 후퇴다. 좌표만 바꾸면 안 되고 셋을 한 묶음으로 처리한다.

- **(3-a) 좌표**: `loadNextChapterForTts`가 `chapters[idx+1]` 대신 플랜의 다음 장을 쓴다. 책이 바뀌면 `setBookCode` + `setChapter`를 함께 부른다(485-486 · 512-513 · 643-644에 이미 있는 패턴).
- **(3-b) 위치 참조**: 현재 로더는 `chapter`를 클로저로 캡처하고, `loadNextChapterRef`는 `start()`에서만 대입된다(TtsContext 727행). 자동 진행은 `start()`를 다시 부르지 않고 큐만 교체하므로(519-532행) 낡은 클로저가 남는다. 지금 동작하는 것은 SearchPanel 763행 effect가 경합에서 이겨 재등록해 주기 때문이다. 위치를 ref에서 읽게 해 경합 의존을 없앤다.

```ts
const posRef = useRef({ bookCode, chapter, planNav });
useEffect(() => { posRef.current = { bookCode, chapter, planNav }; });  // deps 없음 — 매 커밋 갱신
```

  **`posRef`는 이 effect만 쓴다. 로더는 읽기만 한다.** 로더가 반환 직전에 ref를 전진시키면, `setChapter` 커밋 전에 다른 렌더가 끼어들 때 effect가 이전 위치로 되돌려 같은 장이 반복된다. 로더 재호출 간격은 한 장 분량의 재생 시간(가장 짧은 시편 117도 약 10초)이라 한 커밋 지연은 문제가 되지 않는다.

- **(3-c) 763행 effect — 책 가드 완화 + 스테일 가드**. 현재 `tts.currentTrack.bookCode !== bookCode` 가드가 있어 책이 바뀌면 재등록이 막힌다. 플랜 모드의 책 넘김은 선형 이동이라 따라가야 한다. 다만 가드만 열면 안 된다. 이 effect의 deps에 `browseVerses`가 있고 본문은 위치 변경보다 한 왕복 늦게 도착하므로(1152-1173행), 첫 발화 시점의 `browseVerses`는 아직 이전 위치다. 같은 책에서는 "이전 장이 잠깐 들리는" 정도였지만 책이 바뀌면 **다른 책이 읽힌다.**

```ts
// 플랜 모드이고 새 위치가 플랜상 직전/직후 장이면 책 가드를 통과시킨다
const tracks = buildTtsTracks(browseVerses);
if (tracks.length === 0) return;
if (tracks[0].bookCode !== bookCode || tracks[0].chapter !== chapter) return;  // 새 위치 본문 도착 전
```

  목차·QuickNav 점프처럼 **따라가면 안 되는 이동은 그대로 막혀야 한다.** 가드 완화는 플랜상 인접 이동에만 적용한다.

**(4) 렌더**: 본문 상단(장 제목 위)에 `planNav.header`, 하단에 이전/다음 카드 2개(시안 B). 플랜 모드가 아니면 아무것도 렌더하지 않는다.

3초 트리거 자체와 TTS 캐시·프리페치·엔진 라우팅은 손대지 않는다.

## 6. 단계 4 — 그룹

### 6.1 DB

```sql
create table if not exists public.reading_groups (
  id          bigint generated by default as identity primary key,
  name        text        not null,
  invite_code varchar(6)  not null unique,
  plan_id     varchar(20) not null default 'yebom91',
  created_by  text        not null,
  created_at  timestamptz not null default now()
);
create table if not exists public.reading_group_members (
  group_id   bigint      not null references public.reading_groups(id) on delete cascade,
  user_id    text        not null,
  user_name  text,
  joined_at  timestamptz not null default now(),
  primary key (group_id, user_id)
);
create index if not exists reading_group_members_user_idx on public.reading_group_members (user_id);
alter table public.reading_groups enable row level security;
alter table public.reading_group_members enable row level security;
```
`user_name`은 세션 `name` 저장(`verse_notes` 패턴). 표시 이름 변경은 재참여 시 갱신.

### 6.2 API `app/api/reading-groups/`

| 경로 | 메서드 | 동작 |
|---|---|---|
| `route.ts` | GET | 내 그룹 목록 + 각 그룹 멤버 수 |
| `route.ts` | POST `{name}` | 생성 + 생성자 자동 참여. 초대코드 서버 생성(충돌 시 재생성 3회) |
| `join/route.ts` | POST `{code}` | 코드로 참여. 대소문자 무시. 없는 코드 404 |
| `[id]/standings/route.ts` | GET | 멤버별 `{user_id, user_name, doneCount}` 내림차순. 멤버만 조회 가능. 60초 캐시 |
| `[id]/leave/route.ts` | POST | 탈퇴. 생성자는 마지막 멤버일 때만 탈퇴 = 그룹 삭제 |

standings 계산: 멤버 전원의 `reading_progress` + `reading_unit_checks`를 IN 쿼리 2회로 가져와 서버에서 `computeUnitProgress`(lib는 Node에서도 동작). **§2A의 페이지네이션 헬퍼를 반드시 쓴다** — 멤버 합계가 1,000행을 넘는 순간 경고 없이 잘린 부분집합으로 순위가 계산된다.

**동률 정렬은 이름 가나다순이다.** `read_at`을 쓰지 않는다. POST가 재열람마다 `read_at`을 갱신하므로 "마지막으로 연 시각"이 되어, 이미 읽은 장을 한 번 다시 열면 순위가 뒤집힌다. 이름순은 단순하고 조작이 불가능하다.

성능은 지금 우려할 수준이 아니다(1인 평균 28장). 60초 캐시 한 줄만 넣고 더 최적화하지 않는다.

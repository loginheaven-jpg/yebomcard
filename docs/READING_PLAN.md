# 말씀의삶 — 플랜 층 설계

> 예봄교회 성경읽기진도표 91회차(**표준진도표**). 본문 위에 얹는 얇은 순서 층이다.
> 성경 본문·역본·TTS·글꼴 로직은 바꾸지 않는다.
> 2026-09-20 부터 **그룹마다 다른 진도표**를 읽는다 — 아래 §10.

## 1. 무엇을 저장하고 무엇을 파생하는가

**회차 완료는 저장하지 않는다.** 기존 `reading_progress`(장 단위 자동 기록)에서 매번 계산한다.
저장하는 것은 자동으로 알 수 없는 것 하나 — 종이 성경으로 읽었다는 수동 표시(`reading_unit_checks`)뿐이다.

| 데이터 | 위치 |
|---|---|
| 표준진도표 91회차 순서 | `lib/plans/yebom91.ts` (정적 파일, DB 아님) |
| 그 밖의 진도표 | `reading_plans` (2026-09-20 — 교인이 만든 것) |
| 장 단위 읽음 | `reading_progress` (기존, 3초 트리거) |
| 종이로 읽음 | `reading_unit_checks` (RLS on · 정책 0 · service_role 전용) |

## 2. 판정 규칙

```
total     = unitChapters(unit).length
readCount = 그중 readByBook 에 있는 장 수
done      = manual || readCount === total
currentSeq= status !== "done" 인 최소 seq. 없으면 91
```

### nextChapter 와 entryChapter 를 나눈 이유

39회차에서 왕하 15장을 읽으면 3초 트리거가 **15장 전체**를 읽음 처리한다.
40회차(왕하 15:23-17)의 `nextChapter` 는 15장을 건너뛰고 16장을 가리키므로,
그대로 진입시키면 **15:23-끝을 영영 읽지 않고** 40회차가 완료된다.
경계 장이 회차 맨 앞에 오는 6개 회차(40·50·54·69·83·84)가 전부 해당한다.

반대로 "경계 장은 읽음이어도 건너뛰지 않는다" 를 `nextChapter` 에 넣으면 안 된다.
순수 함수라 '이미 제시했음' 을 기억할 수 없어 **같은 장이 영원히 반환되는 고정점**이 된다
(83회차에서 고린도후서를 다 읽는 내내 "다음 읽을 장: 사도행전 19장" 이 굳는다).

| 용도 | 필드 |
|---|---|
| 진도표 행 탭 · 플랜 진입 | `entryChapter` |
| 부제 "다음 읽을 장" · 헤더 | `nextChapter` |

남는 구멍 하나는 인정한다 — 40회차의 나머지를 먼저 다 읽으면 15장이 이미 읽음이라
회차가 자동 완료되어 `entryChapter` 가 호출되지 않는다. 장 단위 판정의 대가다.
대신 **플랜 헤더 칩에 `15:23부터` / `15:22까지` 를 노출**해 사람이 알아보게 한다.

## 3. 경계 장 10개

두 회차 이상에 등장하는 장. 전부 정상이다(절 분할이거나 완전 중복).

| 장 | 회차 | 회차 맨 앞 |
|---|---|---|
| 왕하 15 | 39 · 40 | 40 |
| 왕하 23 | 47 · 50 | 50 |
| 예레미야 40 · 52 | 50 · 51 | 아님 |
| 역대상 9 | 53 · 54 | 54 |
| 역대하 36 | 63 · 69 | 69 |
| 마태 26 · 27 | 46 · 74 | 아님 (완전 중복) |
| 사도행전 19 | 80 · 83 | 83 |
| 사도행전 20 | 83 · 84 · 85 | 84 |

**미수록 1장** — 시편 18. 삼하 22(31회차)와 병행이라 내용은 읽힌다.
다만 통독 화면은 1,189장 기준이라 **91회차를 완주해도 99.9%** 에서 멈춘다.
완주 문구를 통독 % 와 연결하지 않는다.

## 4. 플랜 모드 개입 지점

### 위치는 상태로 들지 않는다

`planMode.idx` 를 상태로 들면 어긋난다. SearchPanel 의 `setChapter`/`setBookCode` 호출은
20곳이 넘고 그중 다수가 플랜과 무관한 점프(공유 딥링크·책갈피·검색 결과·목차 그리드·QuickNavFab)다.
헤더가 "34회차 · 아가 1-8" 을 띄운 채 사용자가 로마서 5장을 보게 된다.

`app/page.tsx` 는 **on/off 와 seq 만** 상태로 들고, `onPositionChange` 로 받은 현재 위치에서
`findPlanIndex` 로 매번 파생한다. `planIdx === -1` 이면 플랜을 벗어난 것이고
헤더가 "플랜에서 벗어남 · N회차로 돌아가기" 로 바뀐다.

SearchPanel 은 다른 뷰에서도 언마운트되지 않으므로 **뷰 판단은 상위가 한다**
(`viewRef.current !== "search"` 면 보고를 무시). `isReadingView` 와 같은 구조다.

### SearchPanel 은 두 곳만 오버라이드한다

단계 2.5 에서 5경로(스와이프·키보드·PC 여백·상단 ◀▶·풀스크린 오버스크롤)가
`goChapter` 하나로 모였다. 그래서 플랜 개입은 **`goChapter` 와 활성 판정 두 곳**이면 끝난다.

활성 판정을 `goChapter` 안에 숨기지 않은 이유가 여기 있다 — 판정은 세 가지 방식으로
소비된다: 렌더 조건(버튼이 사라짐) · `disabled`(흐려짐) · **콜백 `undefined`**(자식이 순환).
숨기면 첫째와 셋째를 재현할 수 없다.

### 인접 중복 장은 방향 무관하게 건너뛴다

53회차 끝(역대상 9)과 54회차 첫 장(역대상 9)이 맞붙어 있어, 그냥 두면 "다음" 을 눌러도
본문이 그대로다. `planStep` 이 양방향으로 처리한다. 플랜 전체에서 이 지점은 여기 하나뿐이다.

### seq 는 진입 시점에 확정하고 플랜 이동으로만 갱신한다

행 탭 진입은 그 행의 seq, 선형 이동은 **도착 항목**의 seq.
역대상 9장을 보고 있을 때 헤더가 53인지 54인지는 어떻게 들어왔는지가 결정한다.

## 5. TTS — 플랜 순서를 따른다

기능을 끄지 않는다. 고령 교인이 가장 많이 쓰는 기능이 플랜 안에서만 죽으면 기능 후퇴다.
좌표만 바꾸면 안 되고 셋이 한 묶음이다.

**(a) 좌표** — `loadNextChapterForTts` 가 플랜의 다음 장을 쓴다. 책이 바뀌면
`setBookCode` + `setChapter` 를 함께 부르되, **DB 조회에 성공한 뒤에만** 옮긴다.

**(b) 위치 참조** — `TtsContext` 는 `start()` 시점에 `loadNextChapter` 를 ref 에 한 번만 담고,
자동 진행은 `start()` 를 다시 부르지 않고 큐만 교체한다. 그래서 콜백이 start() 당시
클로저에 고정된다. 지금 동작하는 것은 아래 (c) effect 가 경합에서 이겨 재등록해 주기 때문인데,
그 effect 는 책이 바뀌면 막힌다 — 플랜 이동은 책을 넘나든다.
위치를 `ttsPosRef` 에서 읽어 경합 의존을 없앤다.

> **`ttsPosRef` 는 effect 에서만 대입한다.** 로더가 반환 직전에 ref 를 전진시키면
> `setChapter` 커밋 전에 다른 렌더가 끼어들 때 effect 가 이전 위치로 되돌려 같은 장이 반복된다.
> 로더 재호출 간격은 한 장 분량의 재생 시간이라 한 커밋 지연은 문제가 되지 않는다.

**(c) 책 가드 완화 + 스테일 가드** — 장 추종 effect 의 `currentTrack.bookCode !== bookCode`
가드를 플랜 모드에서 연다. 다만 **가드만 열면 안 된다.** 이 effect 의 deps 에 `browseVerses` 가
있고 본문은 위치 변경보다 한 왕복 늦게 오므로, 첫 발화 시점의 `browseVerses` 는 아직 이전 위치다.
같은 책에서는 "이전 장이 잠깐 들리는" 정도였지만 **책이 바뀌면 다른 책이 읽힌다.**
트랙이 현재 위치와 다르면 돌아가는 가드를 함께 넣는다.

## 6. 풀스크린

플랜 모드를 유지한다. 오버스크롤 이동은 단계 2.5 에서 `goChapter` 로 통합되어 플랜 순서를
자동으로 따른다. 플랜 헤더만 숨긴다.

완료 시트는 `app/page.tsx` 가 띄우는데 `showFullscreen` 은 SearchPanel 지역 상태이고
외부 채널은 열기 전용이었다. **`fullscreenCloseNonce` 를 추가**해 닫는다.
상태를 끌어올리지 않는다 — 키보드 핸들러와 오버스크롤 배선이 전부 이 지역 상태에 묶여 있다.

## 7. 회차 완료

`onChapterRead(book, chapter)` 같은 **델타로는 판정할 수 없다.** page.tsx 에 기준 집합이 없어
튜플 하나로는 "나머지 12장이 이미 읽혔는지" 를 알 수 없다.
SearchPanel 이 자기 `readChapters` 로 전이를 감지해 **`onUnitComplete(seq)` 하나만** 올린다.

3초 트리거는 재열람마다 발화하므로 한 번 알린 회차는 다시 알리지 않는다.
시트 표시 여부는 `localStorage` 에 기록한다 — 세션 메모리는 새로고침하면 다시 뜬다.

## 8. 인수 조건 (실측)

```
34회차 열왕기상 11장 → 34회차 아가 1장          (정경은 열왕기상 12장)
34회차 아가 8장      → 35회차 잠언 16장          (정경은 이사야 1장)  ← 가장 판별력 높음
3회차  욥기 42장     → 4회차 창세기 1장          (정경은 시편 1장)
53회차 역대상 9장    → 54회차 역대상 10장         (중복 장 건너뜀)
54회차 역대상 9장    ← 53회차 역대상 8장          (역방향도 대칭)
39회차까지 읽은 뒤 40회차 → 진입 왕하 15장 · 표시 왕하 16장
1회차 욥기 1장 ←  없음 / 91회차 요한계시록 22장 → 없음
```

> **주의** — 기본 장 이동이 책 경계를 넘게 된 뒤로 "창세기 50장 → 출애굽기 1장" 은
> 플랜 모드가 아니어도 그렇게 동작한다(그 지점은 플랜 순서 = 정경 순서).
> 플랜 오버라이드를 검증하려면 **아가 8장 → 잠언 16장** 을 써야 한다.

## 9. 그룹

목적은 순위표가 아니라 **동행 확인**이다. 같은 진도표를 읽는 사람들이 서로 몇 회차인지
보는 것까지가 범위다. 벌점·독촉·미읽음 알림은 두지 않는다.

### 진입 때 초대코드 창 (2026-09-11)

말씀의삶에 들어오면 한 번 묻는다 — "함께 읽는 그룹이 있나요?" (`components/GroupCodePrompt.tsx`).
그룹 탭 안의 '초대코드로 참여'만 두면 교인이 찾지 못한다.

| 동작 | 결과 |
|---|---|
| 코드 입력 → 확인 | 그 그룹에 참여(로그인 상태). 코드가 틀리면 창에 이유를 띄우고 그대로 둔다 |
| 비운 채 확인 · 창 바깥 · 뒤로가기 · '그룹 없이 들어가기' | 그냥 진도표로 — 로그인했으면 개인 진도, 아니면 보기만 |
| 로그인 안 한 채 코드 입력 | 코드를 기기에 적어 두고(`yebom_plan_pending_group_code`, 30분) 로그인으로. 돌아오면 **page.tsx 가 말씀의삶을 저절로 열고** 참여시킨 뒤 그룹 탭을 보인다(2026-09-17 — 전에는 교인이 말씀의삶을 다시 찾아 들어가야 했다). 실패하면 이유와 함께 창을 다시 연다 |

- **한 번만 묻는다**: 참여했거나 한 번 건너뛰면 그 기기에서는 다시 묻지 않는다(`yebom_plan_group_prompt` = joined/skipped). 로그인했고 이미 그룹이 있으면(다른 기기에서 참여) 묻지 않고 기억만 한다
- 나중에는 그룹 탭 '초대코드로 참여'로 언제든 참여한다

### 초대링크 (2026-09-17)

코드를 받아 적어 입력하지 않아도 되게 — **링크를 누르고 로그인만 하면 참여**한다. 코드 입력 경로는 그대로 둔다.

- **만들기**: 그룹 탭 카드의 초대코드 오른쪽 **초대링크** 버튼(`ReadingGroupsView` `shareInvite`). 폰은 공유 창(카톡 등)을,
  공유 창이 없는 브라우저는 안내 문구 + 링크를 복사한다. 링크는 `{origin}/?join=코드`
- **받기**(`app/page.tsx`): `join` 을 읽어 **URL 에서 곧바로 지우고**(새로고침·뒤로가기로 두 번 처리하지 않게) 말씀의삶을 열어 코드를 넘긴다(`inviteCode`)
- **참여**(`ReadingPlanPanel`):

| 상태 | 결과 |
|---|---|
| 로그인돼 있음 | 묻지 않고 참여 → 알림. **진도표에 머문다**(지휘부: 링크의 도착지는 진도표 — 처음엔 그룹 탭으로 넘겼다). 실패(코드 틀림·잘린 링크)면 이유와 함께 코드 창 |
| 로그인 안 함 | 초대 모양의 코드 창 — "함께 읽는 그룹에 초대받았습니다", 코드가 채워져 있고 버튼 **로그인하고 참여** 하나. 누르면 코드를 기기에 적고 **확인 창 없이 곧장 로그인 화면으로**(`onLoginNow`). 돌아오면 위 표의 '로그인 안 한 채 코드 입력' 과 같은 길로 참여 |
| '나중에' | 창만 닫는다. 보통 코드 창을 건너뛴 것과 달리 기억하지 않는다 |

- **카카오톡에서 누르면 크롬으로 다시 열린다**(안드로이드 인앱 브라우저 → `PwaInstall` 이 intent 로 크롬에 넘김).
  이때 넘기는 주소는 **처음 열린 주소**(`lib/launchUrl.ts` `LAUNCH_URL`)여야 한다 — page.tsx 가 `join` 을 읽자마자
  주소창에서 지우고, `PwaInstall` 의 effect 는 그보다 뒤에 돈다. 처음 배포(2026-09-17)에서 `location.href` 를 써
  **크롬에 코드 없는 `/` 가 열렸다** — 지휘부가 "링크를 눌러도 말씀의삶에 가지 않는다" 고 보고한 원인. 본문가기(`?goto=`)도 같은 구멍이었다
- **코드를 링크를 받는 순간 기기에 적지 않는다**: 세션 확인이 401(비로그인)이면 `SessionContext` 가 적어 둔 코드를 지운다(남의 그룹 자동 참여 방지). 그래서 메모리에 들고 있다가 **로그인하러 떠나기 직전에** 적는다
- SSO 는 돌아올 때 쿼리 없이 홈(`https://bible.yebom.org/`)으로 온다 — 링크의 코드는 그대로 실려 오지 않는다. 기기에 적어 둔 코드가 그 다리다
- 링크에 그룹 이름을 싣지 않는다 — 이름은 표시용이라 남의 코드에 가짜 이름을 붙인 링크를 만들 수 있다. 참여 뒤 알림이 서버의 진짜 이름을 보인다

### 진도는 그룹에 저장하지 않는다

`reading_groups` / `reading_group_members` 는 **"누가 어느 모임에 속했는가" 만** 담는다.
회차 완료 수는 조회할 때마다 멤버 전원의 `reading_progress` + `reading_unit_checks` 에서
`computeUnitProgress` 로 다시 계산한다(`lib/readingGroups.ts`). 그래서 한 사람이 여러 그룹에
속해도 진도는 하나이고, 그룹을 나갔다 다시 들어와도 숫자가 달라지지 않는다.

**멤버 조회는 `fetchAllRows` 로 페이지네이션한다.** 멤버 합계가 1,000행을 넘는 순간
PostgREST 가 경고 없이 자르고, 잘린 부분집합으로 순위가 계산된다(§2A 와 같은 함정).
1인 평균 28장이므로 36명이면 넘는다 — 가정이 아니라 곧 닿는 규모다.

### 동률은 이름 가나다순이다

`read_at` 을 정렬키로 쓰지 않는다. `app/api/reading-progress` POST 가 **재열람마다**
`read_at` 을 갱신하므로 그것은 "마지막으로 연 시각"이고, 이미 읽은 장을 한 번 다시 열면
순위가 뒤집힌다. 시안 HTML 의 "먼저 마친 사람이 위"는 그래서 폐기했다 —
규칙과 화면 설명이 어긋나면 교인이 순위를 불신한다.

동점자는 **같은 등수**다(1, 1, 3). 이름순은 같은 등수 안의 표시 순서일 뿐이다.
이름이 앞선다고 등수가 앞서면 순위가 이름 경쟁이 된다.

### 초대코드

서버가 만든다. 클라이언트가 정하게 두면 남의 모임 이름을 선점할 수 있다.
혼동되는 `O·0·I·1` 을 뺀 32자 알파벳 6자리(32⁶ ≈ 10억) — 교인이 눈으로 읽고 손으로
입력하는 값이라 공간보다 오독 방지가 앞선다. UNIQUE 충돌 시 3회까지 다시 뽑는다.
입력은 대소문자·공백·하이픈을 무시한다(`normalizeCode`).

### 접근 통제

`[id]/standings` 는 **호출자가 그 그룹 멤버인지 먼저 확인한다.** 이 확인이 빠지면
`id` 를 1씩 올려가며 남의 모임 명단과 진도를 볼 수 있다.
탈퇴는 생성자만 예외 — 다른 멤버가 있는 동안에는 나갈 수 없고(관리자 없는 그룹 방지),
마지막 한 사람이 나가면 그룹째 삭제한다.

순위는 60초 캐시한다. 지금 규모에서 성능 문제가 아니라 **화면을 열 때마다 돌 이유가 없어서**다.
참여·탈퇴는 캐시를 즉시 버린다(`invalidateStandings`) — 새 멤버가 안 보이면 코드가 틀린 줄 안다.
캐시는 프로세스 지역이라 Vercel 인스턴스가 여럿이면 최대 60초 동안 인스턴스별로 다를 수 있다.

### 인수 확인

```
node scripts/verify-reading-groups.mjs      # 서버를 3100 에 띄운 상태에서
```
계정 4개(동률 2 + 하위 1 + 비멤버 1)로 생성·참여·순위·격리·탈퇴 24항목.
동률 두 계정의 이름을 가나다 역순으로 심어 **정렬이 삽입 순서가 아니라 이름순인지** 본다.

## 10. 진도표가 여럿이다 (2026-09-20)

지휘부 결정으로 **그룹마다 다른 진도표**를 읽는다. 교회 진도표는 파일에 그대로 두고 이름만
**'표준진도표'** 가 됐고(`YEBOM91_ID = "yebom91"`), 그 밖의 진도표는 DB(`reading_plans`)에 있다.

### 층을 나눴다

| 파일 | 맡은 것 |
|---|---|
| `lib/plans/engine.ts` | 순수 계산 — `unitChapters` · `computeUnitProgress` · `planStep` · 경계 장 |
| `lib/plans/yebom91.ts` | 표준진도표 **데이터**(엔진을 재수출) |
| `lib/plans/builder.ts` | 만들기 — 자동 분배 · 줄 읽기/쓰기 · 손질 · 검사 · **`sanitizeUnits`** |
| `lib/plans/verseCounts.ts` | 절 수 표(새번역 실측 31,075절) — `scripts/gen-verse-counts.ts` 로 다시 만든다 |
| `lib/plans/registry.ts` | 파일 진도표 + DB 진도표를 한 이름으로 — **`rememberPlan`** |
| `lib/readingPlans.ts` | 서버 — 불러오기 · 목록 · 잠그기 · 그룹 사용 수 |

### 두 가지를 빠뜨리면 조용히 틀린다

1. **회차는 배열 인덱스가 아니다.** `units[seq-1]` 은 회차 번호가 이어질 때만 맞는다 —
   교인이 만든 진도표는 가운데를 빼면 번호가 건너뛴다. `unitBySeq` 로 찾는다.
   회차 수도 `plan.units.length` 다(`91` 을 박으면 막대가 100% 를 넘거나 완주가 안 뜬다)
2. **진도표 객체는 id 마다 하나.** 엔진의 파생값은 진도표 객체를 키로 한 WeakMap 캐시다.
   같은 진도표를 매번 새 객체로 만들면 캐시가 통째로 죽는다 — `rememberPlan(planId, ...)` 만 쓴다

`reading_unit_checks` 조회·기록·삭제에는 **`plan_id` 필터를 반드시 건다.** 회차 번호는 진도표마다 1부터라
필터가 빠지면 다른 진도표의 체크가 섞여 들어온다(화면은 멀쩡해 보인다). 완료 시트를 보여 준 기억
(localStorage)과 그룹 순위 캐시 키도 같은 이유로 진도표별로 갈랐다.

### 자동 분배

`autoUnits(books, unitCount)` — **절 수**를 세어 고르게 나누되 **장은 쪼개지 않는다**(장 단위 읽음 판정이
근거다). 이상적인 누적 절 수에 가장 가까운 장 경계에서 끊고, 회차 수는 정확히 맞춘다(장 수보다 많이 달라면 장 수만큼).
`unitsForVersesPerDay(books, n)` 은 "한 회에 n절쯤" 으로 회차 수를 거꾸로 잡는다.

### 글로 고친다

회차 한 줄은 `창세기 1-3`, `창 50, 출 1-2`, `히브리서`, `열왕기하 15:23-17:41` 처럼 적는다
(`parsePlanLine` ↔ `formatRanges`). **둘은 반드시 왕복해야 한다** — `verify:planbuilder` 가 표준진도표
91회차를 글로 옮겼다가 다시 읽어 확인한다. 예전에 `열왕기하 11-15:1-22` 라는 다시 읽을 수 없는 글을 뱉었다.

### AI 초안

`/api/reading-plans/draft` — 게이트웨이 `gemini-flash` 에 **책 코드와 장 수 표**를 주고
`{mode:"auto",books,unitCount}` 또는 `{mode:"units",units}` 만 받는다. `auto` 면 서버가 `autoUnits` 로 만든다
(모델에게 회차를 다 적게 하면 길고 느리고 틀린다). **저장은 사람이 누른다.**

### 잠그기 · 복사 · 지우기

- **잠금** — 만든 사람 아닌 교인이 회차를 체크한 순간 `locked_at`. 그 뒤엔 이름·설명만 고쳐진다.
  회차를 바꾸려면 **복사해서 내 것으로**. 남이 읽는 중에 회차가 움직이면 그 사람의 진도가 거짓이 된다
- **지우기** — 만든 사람·운영자. 쓰는 그룹이 있으면 **목록에서만 내려간다**(`hidden_at`, 그 그룹은 계속 읽는다).
  수퍼어드민이 `?force=1` 로 끝내 지우면 그 그룹은 **해제**(`plan_id → null`)되고 다시 골라야 한다 —
  **임의로 다른 진도표로 옮기지 않는다**(지휘부)
- **남의 것도 보인다** — 목록에 이름 · 만든 이 · 회차 수만 나온다. 진도는 그룹 안에서만 보인다.
  '나만 쓰기'(`visibility:"private"`)면 목록에서 빠진다

### 표가 없으면

마이그레이션 전이면 목록 API 가 `ready:false` 로 돌아오고(`isMissingTable`), 화면은 표준진도표만 쓰며
만들기 단추가 꺼진다. `supabase-js` 는 없는 표를 `head:true` 로 물으면 오류를 안 내므로
`.select("id").limit(1)` 로 확인한다.

### 인수 확인

```
npm run verify:planbuilder     # 외부 호출 없음 — 범위·분배·줄 읽기·왕복·손질·검사·거르기·엔진 결합
npm run verify:plan            # 표준진도표 91회차 (기존)
```
